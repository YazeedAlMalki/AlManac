## 2. Task A — Lab catalog: import-job records

**Status: assessed, parked. Not built.** This is a real gap, not a deferral.

§2.5 distinguishes an **import job** from a **sync cursor**, and the distinction is
load-bearing: a job has a start, an outcome and a row count; a cursor has a
position. `LabReportCSVImport` parses and returns. It does not record that it ran,
what it matched, or how many rows it left unmatched. `LabCatalog.match` is
ambiguity-aware and deliberately does **not** auto-resolve — so unmatched rows are
a normal, expected outcome with no record anywhere.

### The blocker you must not resolve on your own

**Does a failed import leave a job row that says so, or nothing at all?**

That is a product decision, and it was deliberately not made. The two defensible
answers:

- **Leave a row.** The user can see that a report they imported is half-matched
  and revisit it. Costs a growing table and a status vocabulary to maintain.
- **Leave nothing.** A job is a successful act; a failure is a message they
  already saw. Simpler, and the cost is that an import that matched three of
  forty analytes three weeks ago leaves no trace.

**Ask Yazeed. Do not pick one and move on.** Park it with the reasoning recorded
in `docs/features/laboratory-catalog-coverage.md` if you get no answer.

### If you do build it

- Migration **046** (045 is taken). §2.5 / §5.25 for the shape; follow the
  Migration044 precedent for documenting a spec contradiction rather than resolving
  it silently.
- A store, a status vocabulary as an explicit enum (not a free-text column), and a
  place on the import screen to show it. `LabReportCSVImport` is the only caller.
- **Wire it as a pull-based reconciliation**, not a call site in the import button.
  `docs/features/fasting.md` records what manual multi-site wiring costs this repo
  (six hydration paths, and the note that "the seventh path added later will be the
  one that forgets").
- Extend `docs/acceptance-checklist.md` §2 with what you drove.

## 6. Task E — Body composition: cards with goals, meter, history

**Currently:** `MeasurementsView` in `MoreViews.swift` is a flat list of rows plus
a "Log body measurement" button that opens a `Picker` — one metric at a time. That
is the "dropdown list" you want replaced. Body composition is stored as
`BodyCompositionMeasurement` rows with a **string** `metric`
(`weight | body_fat_pct | lean_mass_kg | skeletal_muscle_kg | visceral_rating`).

**The blocker:** `goal_target_snapshot` (§5.2) **does not exist**. No table, no
store, no code. BRD §6.10 wants Bulk/Cut/Maintain/Performance with Mifflin-St Jeor
targets and immutable per-period snapshots. A meter needs a target; there is
nothing to be a target.

### Ambiguity to resolve first

**"body fat = 33kg, goal = 18kg"** — 33 → 18 kg is a body-**weight** goal, not body
fat. Body fat is stored as a *percentage* (`body_fat_pct`) and is not sensibly
expressed in kg. Confirm which metric the example means before building the card
layout around it.

### Also a product decision — do not guess

- **What happens to a metric with no target set?** A meter with no target is either
  hidden, or shown empty. Both are defensible; neither is free. This repo's
  convention is to not invent a number nobody chose, so the default is probably
  "no target, no meter" — but a card grid where half the cards lack the feature
  the feature was built for is a design question, not a data question.
- **Is the target per-metric or per-goal?** A "cut" goal implies a body-fat
  target; it does not imply a weight target, or a lean-mass one. Per-metric
  targets inside one goal snapshot is the obvious reading. Confirm.

### Build notes

- Migration **046** for `goal_target_snapshot` if not already taken.
- §5.2 says rows are **immutable** — a new row per goal change, never updated.
  That is a real constraint; honour it rather than upserting.
- One card per metric with a defined subject (weight, body fat, lean mass,
  skeletal muscle, visceral rating), a value, a meter, and history. "History
  progress of target" means a *series toward a goal*, not a list of readings —
  which makes it a trend question, and `TrendEngine` already exists.
- A meter is a **new design-system component**. `DesignSystem.swift` has
  `AlmanacMetrics`, `AlmanacStatusTone` and existing `AlmanacRule`/`AlmanacStatusMark`
  to sit alongside. Read the file first. VoiceOver and Dynamic Type are not
  optional on a meter — a bar that conveys a number and has no label conveys
  nothing to a screen reader.
- Wire pull-based, as in Task A.

## 7. Task F — Profile fields

**Currently:** `ProfileView` (`MoreViews.swift`) is five text fields —
displayName, dateOfBirth, biologicalSex, heightCm, sports (comma-separated free
text). `ProfileStore` has one `update…` method per field. The `profile` table is
§5.1: `displayName`, `dateOfBirth`, `biologicalSex`, `heightCm`, `sports` (JSON
array). No blood type, no allergies, no training experience anywhere in the repo.

### Requested

| Field | Note |
|---|---|
| First name, Last name | `displayName` is one field. Splitting is a migration + a display-name decision (which do you show?). |
| DOB, height, sex | Exist. `sex` is free text today; you asked for Male/Female, which is a closed set — a validation change, and note the schema already allows `other | not_set`. |
| Years of training | New. Novice/beginner/moderate/expert. |
| Blood type | New. |
| Food allergies | New. **Nothing in the repo models allergies at all.** |
| Preferred sports | Exists as a JSON array, entered as comma-separated text. You want a multi-select from a real list (weight lifting, football, volleyball, basketball, fencing, padel, …). |

### Three things to settle before building

1. **All mandatory — including on an existing install.** Making DOB, sex and
   height mandatory is fine for a new user and wrong for a user who has been
   logging for a year. A hard gate on save would lock them out of their own data.
   Decide: a first-run setup flow, a soft "complete your profile" prompt, or a
   mandatory gate that existing users are grandfathered past. **This is a product
   decision.**
2. **Food allergies carry a safety weight the rest of this app does not.** If the
   app later surfaces a food suggestion, an allergy list is a correctness and a
   harm question, not a preferences field. Building it as a plain text field with
   no vocabulary, no severity, and no statement about what the app does with it
   is the version most likely to cause harm. Ask what it is *for* before building
   it.
3. **Sex is a closed set but the schema is not.** `male | female | other |
   not_set` is what §5.1 allows. Restricting to Male/Female in the UI while the
   column says otherwise is fine; writing a value the column does not list is not.

## 9. Working practices that have mattered here

- **Read the source before believing a status claim.** Two handoffs in a row
  arrived wrong. The `dayType` blocker was fiction; the README's three false claims
  sat in the repo for months.
- **Distinguish bug from product decision, and don't guess at decisions.** The
  import-job status question, the mandatory-profile-fields question and the
  metric-identity question are all in this file because answering them is not an
  agent's call. Park them with the reasoning recorded.
- **Tests that assert a bug are worse than no tests.** When a test and reality
  disagree, work out which is which before editing either. A test written in §1
  that lost half its sample to a window boundary is a reminder that a fixture bug
  wears the costume of a code bug.
- **Dependency direction is deliberate.** Hydration and Nutrition must not learn
  Fasting exists. New wiring goes in a wrapper beside the base store —
  `FastingAwareHydrationLog`, `FastingAwareNutritionLog`. A new task that has to
  "just reach into" a foundational store is usually a wrapper asking to be written.
- **Prefer pull-based, idempotent reconciliation** (`ensureCache`, `ensureCycle`,
  `ensureDay`, `NotificationPlanner.plan()`). A missed call site should cost one
  stale refresh, not a permanently wrong state.
- **Record decisions and gaps in `docs/features/*.md` and
  `docs/implementation-status.md` as you go**, not at the end.
- **Say what was not run.** A step marked PASS that was not driven is worse than a
  step marked UNRUN.
