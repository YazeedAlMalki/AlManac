## 2. Task A — Lab catalog: import-job records

**Status: assessed, parked. Not built.** This is a real gap, not a deferral.

§2.5 distinguishes an **import job** from a **sync cursor**, and the distinction is
load-bearing: a job has a start, an outcome and a row count; a cursor has a
position. `LabReportCSVImport` parses and returns. It does not record that it ran,
what it matched, or how many rows it left unmatched. `LabCatalog.match` is
ambiguity-aware and deliberately does **not** auto-resolve — so unmatched rows are
a normal, expected outcome with no record anywhere.

### The one question for Yazeed, in plain words

Yazeed was asked this and did not follow the first phrasing, so here it is
concretely.

**Today, when you import a lab report, Almanac already works out exactly how it
went** — `LabCSVImportResult` carries `observationsCreated`, `invalidRows`,
`reportConflicts`, and the rest. It shows you the outcome once and then throws
the numbers away. Nothing is written down.

So the question is only this: **should Almanac write those numbers down so you
can look at them later?**

- **Yes** — you could see "Tuesday: 32 of 36 lines imported, 4 didn't match"
  in a list, and go back and fix the 4. Costs a table, a status vocabulary and
  a screen.
- **No** — an import is a thing that happened; you saw the result at the time.
  Cheaper. The cost is that an import that half-failed three weeks ago leaves
  no trace at all, and you'd never know you lost data.

**Ask Yazeed. Do not pick one and move on.** Park it with the reasoning recorded
in `docs/features/laboratory-catalog-coverage.md` if you get no answer.

### If you do build it

- Migration **046** (045 is taken). §2.5 / §5.25 for the shape; follow the
  Migration044 precedent for documenting a spec contradiction rather than resolving
  it silently.
- A store, a status vocabulary as an explicit enum (not a free-text column), and a
  place on the import screen to show it. `LabReportCSVImport` is the only caller.
- **Wire it as a pull-based reconciliation**, not a call site in the import button.
  `docs/features/fasting.md` records what manual multi-site wiring costs this repo
  (six hydration paths, and the note that "the seventh path added later will be the
  one that forgets").
- Extend `docs/acceptance-checklist.md` §2 with what you drove.

### Answered by Yazeed: percentage by default, kg behind a toggle

> "by default let it show as a percentage but have a tab to switch to weight
> unit in kg"

So the card grid shows each metric in its natural unit, with a control that
switches between them. Two things follow, and one needs a decision:

- **Body fat in kg is derived, not measured.** The database stores
  `body_fat_pct` only. Fat mass in kg is `bodyWeightKg × bodyFatPct / 100` — a
  number the app computes from two other numbers. It is a legitimate thing to
  show, but it is not a measurement and must not be stored as one or trended as
  one. Label it as derived, or show "—" where weight is unknown.
- **The toggle is app-wide or per-card?** "A tab to switch" reads as one control
  for the screen, not a switch on every card. App-wide is simpler, and it means
  the preference belongs in `profile` (see Task F) so it survives leaving the
  screen. **Confirm app-wide.**

### Still a product decision — do not guess

- **What happens to a metric with no target set?** A meter with no target is either
  hidden, or shown empty. Both are defensible; neither is free. This repo's
  convention is to not invent a number nobody chose, so the default is probably
  "no target, no meter" — but a card grid where half the cards lack the feature
  the feature was built for is a design question, not a data question.
- **Is the target per-metric or per-goal?** A "cut" goal implies a body-fat
  target; it does not imply a weight target, or a lean-mass one. Per-metric
  targets inside one goal snapshot is the obvious reading. Confirm.

### Build notes

- Migration **046** for `goal_target_snapshot` if not already taken.
- §5.2 says rows are **immutable** — a new row per goal change, never updated.
  That is a real constraint; honour it rather than upserting.

## 8. Performance — a hard constraint, not a nice-to-have

> "remember, whatever you do, dont make the app heavy or lag"

**Yazeed's instruction. It is a requirement, not a preference.** It is its own
section because the last session shipped a real instance of it, and the fix is
the worked example for everything in this list.

### The bug that prompted this: a 140-query scheduling pass

`NotificationPlanner` correctly evaluates suppression at each notification's own
fire instant — two of Appendix B's five axes carry their own timestamps and need
the instant. It did that by calling `context(at:)` **once per candidate**, and
each call issued about seven queries: active fast, two shift occurrences, two
days of sleep episodes, the open readiness cycle, its record.

A 48-hour window plans twenty-odd notifications. That is **~140 queries for one
pass** — and the pass runs on **every foreground activation**. Correct, and far
too expensive.

**The fix, and the pattern to copy.** Three of the five axes cannot vary within a
pass at all: a dry fast is active at every candidate's fire instant or at none of
them, and today's readiness is final or it is not. Only `isNightShift` and
`isPostShiftSleep` depend on the instant. So:

- `NotificationSuppressionContextAssembler.nowOnlyAxes()` reads the three invariant
  axes **once** as a separate type (`NowOnlySuppressionAxes`, deliberately not a
  `NotificationSuppressionContext` with two fields left false, so it cannot be
  passed to `shouldSuppress` by accident and silently suppress nothing).
- `nightOccurrences(around:)` and `postShiftEpisodes(around:)` read the rows the
  two varying axes need **once**; `isWithinNightShift(at:occurrences:)` and
  `isWithinPostShiftSleep(at:episodes:)` answer from memory.
- Per candidate: **zero queries.**

Same answers, ~4 queries per pass. Pinned by
`Tests/AlmanacCoreTests/NotificationPlannerCostTests.swift`, whose most important
test is `batchedEqualsPerInstant` — a performance fix that changed behaviour
would be caught.

**The general rule: ask what varies within the pass, read the rest once.**

### Where to look before you build

| Watch for | Where it already exists |
|---|---|
| A per-item store call inside a `for` over items | `ReadinessBaselineService.validDays(on:facts:)` calls `shifts.occurrence(for:)` per day. Bounded today; a longer window makes it linear. |
| A per-candidate read inside a `filter` | The bug above. `NotificationPlanner.plan` was the worst case in the repo. |
| A whole-history scan on a foreground path | `ReadinessBaselineService.ValidDayFacts.validDays()` — three `SELECT DISTINCT` over all history, because §9.7 says "from first use". It is correct and it is three queries; do not add a fourth per day. |
| A query inside a `filter` closure that itself calls a store | `ramadanResolution` calls `fastSchedules.schedules(activeOnly: true)` once per candidate day. Fine at 30 days, linear at 3,650. Hoist it. |
| Work on the main actor | Every model is `@MainActor`. Reads and writes are sync. A scan that takes 40 ms is a 40 ms frame. |

### Rules for the new work

- **A card grid of five metrics must not be five store reads.** One query, five
  values.
- **A meter's fill is a value, not an animation.** A `ProgressView` or a
  `Rectangle().frame(width:)` bound to a computed fraction. No `withAnimation`
  loop, no `TimelineView` driving it, no per-frame state. If it looks static it
  should be static.
- **History-toward-target is a trend, and `TrendEngine` already exists.** Do not
  reimplement it per card.
- **No `Timer`, no polling, no background refresh loop.** This repo's answer to
  "when does this refresh" is a pull-based reconciliation on foreground
  (`ensureCache`, `ensureCycle`, `plan()`), and that is also the cheap answer.
- **Measure, do not assume.** If something feels slow, count the queries before
  optimising and the frame time before caching. A guessed optimisation on a path
  that was never hot is a new bug.

## 10. Working practices that have mattered here

- **Read the source before believing a status claim.** Two handoffs in a row
  arrived wrong. The `dayType` blocker was fiction; the README's three false claims
  sat in the repo for months.
- **Distinguish bug from product decision, and don't guess at decisions.** The
  import-job status question, the mandatory-profile-fields question and the
  metric-identity question are all in this file because answering them is not an
  agent's call. Park them with the reasoning recorded.
- **Tests that assert a bug are worse than no tests.** When a test and reality
  disagree, work out which is which before editing either. A test written in §1
  that lost half its sample to a window boundary is a reminder that a fixture bug
  wears the costume of a code bug.
- **Dependency direction is deliberate.** Hydration and Nutrition must not learn
  Fasting exists. New wiring goes in a wrapper beside the base store —
  `FastingAwareHydrationLog`, `FastingAwareNutritionLog`. A new task that has to
  "just reach into" a foundational store is usually a wrapper asking to be written.
- **Prefer pull-based, idempotent reconciliation** (`ensureCache`, `ensureCycle`,
  `ensureDay`, `NotificationPlanner.plan()`). A missed call site should cost one
  stale refresh, not a permanently wrong state.
- **Record decisions and gaps in `docs/features/*.md` and
  `docs/implementation-status.md` as you go**, not at the end.
- **Say what was not run.** A step marked PASS that was not driven is worse than a
  step marked UNRUN.
